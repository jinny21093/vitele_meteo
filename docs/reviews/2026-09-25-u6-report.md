## 2. РЕШЕНИЯ — ДО КОДА (как заказано в задании)

### S1. Коннект/семафор при стриминге export.csv (вопрос «коннект живёт дольше обработчика»)

**Выбрано:** генератор НАРУЖУ не возвращается — `_api_export` сам ведёт цикл
`fetchmany(500)` → csv.writer → chunked-фрейм → write+flush. Коннект открывается
`db_open` ПОСЛЕ всех валидаций (400-пути) и закрывается в `finally` ПОСЛЕ конца
или обрыва стрима: **время жизни коннекта == времени жизни обработчика**,
«дольше обработчика» не возникает.

-   Семафор: слот берётся в `process_request` ДО создания потока и освобождается
    в `finally` `process_request_thread` ПОСЛЕ завершения обработчика → слот
    занят ровно время стрима. Это единственный long-lived обработчик
    (§5.0 v1.2.8); MAX_CONCURRENT=20, профиль «≤5 пользователей» (§7) — запас.
-   Зависший клиент: HANDLER_TIMEOUT=10 — per-op inactivity сокета; write в
    полный TCP-буфер даёт socket.timeout → исключение → `finally` закрывает
    коннект → слот свободен. Утечки слотов нет; общего wall-clock дедлайна нет
    (стриминг легитимен, пока сокет активен — §5.0).
-   WAL: длинный read-стрим не блокирует коллектора; `BEGIN` перед COUNT даёт
    единый read-снапшот COUNT+SELECT (иначе авто-commit дал бы два снапшота).
-   Ошибка БД ДО заголовков (db_open/BEGIN/COUNT/SELECT) — штатный 503 через
    do_GET. ПОСЛЕ заголовков честный 503 невозможен: best-effort терминальный
    chunk (файл обрезается), ERROR в лог, соединение закрывается —
    задокументировано в docstring и §5.9 v1.2.8.
-   На экспорт-ответе явно `Connection: close` (send_header сам ставит
    close_connection) — после chunked-фрейминга keep-alive не открываем.

### S2. wmeta-whitelist: НОВЫЙ GET /api/settings, /api/meta НЕ тронут

**Выбрано:** отдельный эндпоинт `/api/settings` — конверт структурно равен
`/api/meta`, но `wmeta` фильтруется на сервере по `WMETA_VISIBLE` = (units, tz,
tz_offset_seconds, gdd_tbase_c, ok_total, err_total, last_ok, schema_version) —
РОВНО список ревьювера. **Почему не фильтровать /api/meta:** контракт §5.7
(«wmeta объект» целиком) документирован и используется ВСЕМИ страницами
(app.js берёт оттуда `tz_offset_seconds`) — серверная фильтрация там была бы
ломающим изменением контракта. `db_health` идёт в конверте /api/settings
отдельным ключом (парсится из НЕфильтрованного словаря — он не элемент
wmeta-карточек). Деградация по таблицам — паттерн m-5 из _api_meta.

**Следствие (решение):** предложение «результат POST кэшировать в wmeta
db_health» ОТКЛОНЕНО — это была бы ЗАПИСЬ из UI (нарушение принципа §0.4

`PRAGMA quick_check` на query_only-коннекте (это чтение — принцип не нарушен)

должен. Владелец ключа — этап B (когда добавит; сегодня ключа нет → экран
честно показывает жёлтое «Проверка БД: не проводилась»). Результат кнопки
живёт в карточке до конца сессии на клиенте (без серверного кэша).

### C2. Пробник перед скачиванием (HEAD → 501)

**Выбрано** предложение ревьювера: лёгкий GET-пробник с теми же параметрами и
`limit=1`. Для этого export.csv поддерживает опциональный `limit` (int
1..100000, placeholder), который применяется ПОСЛЕ pre-COUNT → **пробник
проходит ту же проверку 413** (эстимация от COUNT полного окна, от limit не
зависит). Пробник 200 (заголовок + 1 строка) → `window.location` на полный URL
(без limit); 413 → баннер с числом строк из JSON-тела; 401/сеть → баннер.
TOCTOU-оговорка: между пробником и скачиванием размер теоретически может
подрасти (коллектор пишет) — тогда браузер получит 413-JSON вместо файла;
редко, повтор кнопки решает. Зафиксировано в §4.6 v1.2.8.

### Сверка окна export со спекой §5.9 (вопрос U6-T1)

Спека v1.2.7 §5.9: «Окно ≤ 31 дня», 413 при count > 100 000, BOM опционально
(`?bom=1`). Задание U6: окно ≤ 366 дней, 413 по эстимации байт > 300 МБ, BOM
не писать (A10/U8). **Принято задание U6** (оно новее и покрывает три таблицы):
окно > 366 д → **400** общим гвардом `_required_window` (ответ на вопрос
ревьювера: да, «>366 → 400»; 413 — про РАЗМЕР, не про окно), размер реального
ответа гвардит pre-COUNT-оценка 300 МБ. Несовместимости с v1.2.7 §5.9
зафиксированы в changelog v1.2.8: 31 д → 366 д; count>100000 → байты+X-Export-Rows;
`?bom` отменён; filename `weather-YYYY-MM-DD.csv` → `weather-<type>-<from>-<to>.csv`.

      btn.disabled = false;
    }
  }

  /* --- U6-C3: проверка БД (свой fetch — см. шапку) --- */
  function openModal() {
    $("set-modal-body").textContent = "";
    $("set-modal-body").appendChild(el("span", "muted", "выполняется…"));
    $("set-modal").classList.remove("hidden");
  }
  function fillModal(rows) {
    const body = $("set-modal-body");
    body.textContent = "";
    const ok = rows.status === "ok";
    body.appendChild(el("div", "badge " + (ok ? "ok" : "bad"),
      ok ? "quick_check: ok" : "quick_check: проблемы"));
    body.appendChild(el("p", "muted",
      "Выполнено за " + rows.duration_ms + " мс; ответов: " + rows.row_count +
      (rows.truncated ? " (показаны первые " + rows.rows.length + ")" : "")));
    const list = el("ul");
    for (const r of rows.rows) list.appendChild(el("li", null, String(r)));
    body.appendChild(list);
  }
  function rememberSession(rows) {
    sessionCheck = {
      status: rows.status,
      whenText: new Date((Math.floor(Date.now() / 1000) + tz()) * 1000)
        .toISOString().replace("T", " ").slice(0, 16) + " TZ дачи",
    };
  }

  async function checkDb() {
    if (!window.confirm("Проверка целостности БД (PRAGMA quick_check) может " +
                        "занять несколько секунд. Запустить?")) return;
    openModal();
    const ac = new AbortController();
    const timer = setTimeout(() => ac.abort(), CHECK_TIMEOUT_MS);
    let res;
    try {
      res = await fetch("/api/check-db", { method: "POST", signal: ac.signal });
    } catch (e) {
      W.banner("Проверка БД не отвечает: " +
        (e.name === "AbortError" ? "таймаут клиента" : e.message), "bad");
      $("set-modal-body").textContent = "";
      $("set-modal-body").appendChild(el("span", "muted", "запрос не выполнен"));
      return;
    } finally { clearTimeout(timer); }
    let payload = null;
    try { payload = await res.json(); } catch (e) { /* не JSON */ }
    if (res.ok && payload) {
      fillModal(payload);
      rememberSession(payload);
      renderDbh(null);            // перерисовать карточку с sessionCheck
      return;
    }
    $("set-modal-body").textContent = "";
    if (res.status === 429) {
      const ra = parseInt(res.headers.get("Retry-After"), 10) || 60;
      W.banner("Проверка БД: не чаще 1 раза в минуту — подождите " + ra + " с",
               "warn", true);
      $("set-modal-body").appendChild(el("span", "muted",
        "лимит: 1 проверка в минуту"));
    } else if (res.status === 503 && payload && payload.error === "check timed out") {
      $("set-modal-body").appendChild(el("span", null,
        "Превышен таймаут (60 с) — проверка прервана. Повторите позже; " +
        "повтор возможен не раньше, чем через минуту."));
    } else if (res.status === 503) {
      $("set-modal-body").appendChild(el("span", "muted",
        "БД недоступна (503)"));
    } else {
      $("set-modal-body").appendChild(el("span", "muted",
        "HTTP " + res.status));
    }
  }

  /* --- init --- */
  function init() {
    $("set-from").value = defaultFrom();
    $("set-to").value = defaultTo();
    $("set-export-btn").addEventListener("click", probeExport);
    $("set-check-btn").addEventListener("click", checkDb);
    $("set-modal-close").addEventListener("click",
      () => $("set-modal").classList.add("hidden"));
    $("set-modal").addEventListener("click", (e) => {
      if (e.target === $("set-modal")) $("set-modal").classList.add("hidden");
    });
    $("refresh").addEventListener("click", () => {
      if (poller) poller.refreshNow();
    });
    poller = W.poll(loadSettings, POLL_MS);
    W.refreshHeader();
  }

  W.ready.then(init).catch((e) => {
    W.banner("Инициализация страницы не удалась: " + e.message, "bad");
  });
})();
