# Метеостанция 192.168.8.101: положение дел и план — бриф для ИИ

_Составлено 2026-09-15 ~23:00 MSK агентом-исполнителем по просьбе владельца. Цель — полный контекст проекта одним документом: что есть, в какой среде, что решили, что будем делать._

## 1. Объект

- Дачный дом, LAN 192.168.8.0/24 (роутер Keenetic). Wi-Fi метеостанция **192.168.8.101** (MAC `D8:BC:38:A6:E6:14`), модель протоколом не сообщается.
- HTTP API (порт 80): `GET /client?command=record` — полный срез всех датчиков одним JSON (~921 Б, 23 значения строками, UTF-8 **без** charset в заголовке — декодировать явно). Опрос ограничен производителем: **не чаще 10 с**; замеренная задержка ответа 15–95 мс. POST-эндпоинты станции (calibrate/register) не трогаем. `GET /config?command=connect_status` и `/unit.html` — для диагностики.
- Единицы: давление — **мм рт. ст.** (решение владельца, станция их и выдаёт), °C, м/с, мм, Вт/м².
- **Своей истории станция не хранит** — внешний сбор обязателен, потерянный замер невосстановим.

## 2. Что уже работает (этап 1 «сбор и хранение», готово 15.09)

- Исполнитель — ИИ-агент (я), доступ через SSH-цепочку outpost→vitele; изменения на устройствах — только с одобрения владельца.
- На сервере vitele в `~/weather-dash/`: `weather_poller.py` (Python 3.11, **stdlib-only**: urllib/json/sqlite3), запуск **cron раз в минуту**, INSERT OR REPLACE (идемпотентно), самодиагностика (WARN при новых полях датчиков в JSON и при смене единиц на станции).
- **БД v1** (SQLite `weather.db`): таблица `weather(ts INTEGER PRIMARY KEY — epoch UTC` + 23 REAL: indoor/outdoor temp+hum, `pressure_abs/rel_mmhg`, ветер 8 колонок (мгновенный/gust/avg2/avg10 + направления, max daily), дождь 7 (rate, hour/day/week/month/year, total), `light_wm2`, `uvi`) + `battery TEXT`; таблица `wmeta(k,v)`: schema=1, units, ok_total, last_ok.
- **Свежий статус** (на момент брифа): 40 замеров за первые 40 минут, провалов >90 с — **0**, автопрогоны cron подтверждены; файл 25 КБ. Прогноз роста ≈150 МБ/год при минутном опросе — ретеншн не нужен.

## 3. Среда исполнения (vitele — единственный исполнитель всех компонентов)

- Debian 12 (systemd 252), x86_64, **1 vCPU** (i7-9700 @3.00 ГГц), 4 ГБ RAM (доступно ~2.6 ГБ), swap 1 ГБ, load ~0.05.
- Диск 19 ГБ, занято 59%, **свободно ~7.4 ГБ** — главный ограничитель (считать размер бэкапов).
- Python 3.11.2 + pip 23, **SQLite 3.40.1** (CLI и Python; оконные функции ≥3.25 и math-функции ≥3.35 есть), cron, systemd; venv доступен, но поллер сознательно stdlib-only.
- Хост уже несёт: Uptime Kuma (56 мониторов), snmp-dash (:8088), netlog (syslog-коллектор), MQTT (mosquitto), MariaDB, apache/php-fpm, pm2-приложение, ZeroTier. Т.е. «минимальный» хост, а не пустой.
- Сервер внутри LAN дачи, наружу ничего не торчит; интернет есть.

## 4. ТЗ v2 (`weatherboard_v2_analitic.md`, составлено владельцем с DeepSeek) — принято к работе

Суть: **(а)** схема v2 — surrogate id + `UNIQUE(ts)` (retry-safe), WAL + `synchronous=NORMAL` + `busy_timeout`, таблица версий схемы, журнал коллектора `collector_log` (status/latency/bytes), `events` (19 типов: FROST, FOG, STORM_APPROACH, HEAVY_RAIN, SENSOR_STUCK/DRIFT/MISSING, BATTERY_LOW…), `forecast` (persistence/Zambretti/Sager/ML), материализованные агрегаты `v_hourly`/`v_daily`/`v_monthly`/`v_yearly` + вьюха коротких трендов; **(б)** L1-производные поля считаются в коллекторе при ингесте: точка росы (Magnus), wind chill (JAG/TI), heat index (Rothfusz), 16 румбов, ΔP, wind run, расчётный rain rate через приращение типпера (квант 0.1 мм, rate-порог 0.2 мм/ч отвергнут), rain_event, GDD (Tbase=5 для дачи); **(в)** ветер — только векторное усреднение и мода по румбам, арифметическое среднее направлений запрещено; **(г)** REST API (`/now`, `/history`, `/daily`, `/events`, `/forecast`, `/summary`, `/insights`, `POST /ask`) — LAN-only + basic auth; **(д)** наблюдаемость: systemd, бэкапы `VACUUM INTO`, heartbeat.

## 5. Правки агента к ТЗ v2 (согласованы с владельцем)

1. systemd-юнит: путь `/home/auditbot/...` (в ТЗ `/home/vitele` — такого юзера нет).
2. `WatchdogSec=180` без sd_notify в питон-коде = вечный рестарт-луп → стартуем без watchdog.
3. Миграция v1→v2 проще описанной: `ts` в v1 **уже epoch UTC** (ISO-парсинг не нужен); накоплено меньше суток — перенос тривиален.
4. `idx_weather_id` избыточен (AUTOINCREMENT PK уже даёт индекс) — убрать.
5. Вьюха трендов: `LAG(...,60)` — это 60 **строк**, а не минут; при провалах данные врут → тренды считать по временным окнам (диапазоны ts).
6. Prometheus не ставим (хост и так нагружен); наблюдаемость = `collector_log` + heartbeat в уже работающий Uptime Kuma.
7. Бэкапы: 30 дней без сжатия = ~4.5 ГБ при 7.4 ГБ свободных → **gzip + ротация 14 дней** (ок владельца).
8. **Интервал опроса 60 с** (не 30 из ТЗ): датчики станции сами обновляются 16–60 с, чаще бессмысленно.
9. LLM-функции (/ask, NLP-сводки) требуют внешний LLM API + ключ — пока исключены (см. ниже).

## 6. Решения владельца (15.09, финальные для планирования)

1. **Без LLM сейчас** — NLP-сводки, /ask, ML-прогноз, детектор аномалий, инсайты = хотелки на будущее (бэклог).
2. **Интервал опроса остаётся 60 с.**
3. **Бэкапы — ок**: ежедневно `VACUUM INTO` (+gzip), ротация ~14 дней; NAS нет, внешний rsync не делаем; потеря максимум суток сырых данных приемлема (дашборды смотрим вживую ежедневно).
4. **DHCP-резерв .101 на Keenetic владелец сделает сам** (веб-панель).

## 7. План внедрения (этапами, не «за раз»)

- **Этап A (P0, следующий шаг):** миграция БД на схему v2 (с бэкапом и сценарием отката), коллектор v2 (L1-поля, `collector_log`, retry-safe запись), systemd-юнит вместо cron, первичные события (FROST/HARD_FREEZE, SENSOR_MISSING, BATTERY_LOW, RAPID_TEMP_*), ежедневный бэкап-джоб. Критерий готовности: БД v2 наполняется, события генерируются, сервис переживает рестарт.
- **Этап B (P1):** материализаторы `v_hourly`/`v_daily` (+месяц/год) по cron, инкрементально; тренды по временным окнам; прогнозы persistence + Zambretti (+Sager днём); REST API-скелет (LAN-only, basic auth); heartbeat в Uptime Kuma. Критерий: API отдаёт агрегаты, Kuma видит живость.
- **Этап C (P2, отложен):** /ask с read-only валидатором, NLP-сводки — вернуться, когда владелец решит вопрос LLM-провайдера.
- **Этап D (P3/P4, бэклог):** ML-прогноз (LightGBM/Prophet), Isolation Forest, корреляции; условие — ≥30 дней непрерывной истории; реализуемость на 1 vCPU оценить отдельно.
- **UI/дашборд:** отдельный документ `weather-ui-spec.md` (у владельца); внедряем **после** этапа B — сначала данные и хранение, как и договаривались.
- Дисциплина: один этап = одна сессия с бэкапом/снепшотом и откатом; между этапами — неделя-две живой проверки.

## 8. Что сверить с DeepSeek перед этапом A

- План этапов A–B: нет ли пропущенных подводных камней (миграция cron→systemd, WAL на слабом хосте, инкрементальные материализаторы, векторное усреднение ветра в hourly-агрегатах).
- Sanity-check решений: 60-с интервал; бэкап = daily VACUUM INTO + gzip, ротация 14 дней; отказ от Prometheus в пользу Kuma-heartbeat; откладывание LLM/ML-слоя до ≥30 дней истории.
- Замечания к самому ТЗ v2 (разделы 1–6 выше) учесть до старта этапа A; следующий входной документ от владельца — `weather-ui-spec.md`.
